# Encrypted backup and restore drill

Status: tooling is reviewable; scheduled protection is **not operational**. No GitHub secrets, recipient, schedule flag or hosted restore have been configured by this change. A successful encrypted artifact is not proof that the application can be restored.

## What the job saves

The workflow uses a hosted GitHub runner, not your computer. It exports Supabase roles, application schema and database data (including Auth/Storage rows), a separate managed `auth,storage` schema reference, migration history, bucket/object inventory, core row counts and every inventoried Storage file. Each file has a SHA-256 checksum inside the encrypted manifest. The sole uploaded artifact is a `.tar.age` file. Object names, account data, SQL and checksums stay inside encryption.

The Supabase CLI is pinned to [2.75.0](https://github.com/supabase/cli/releases/tag/v2.75.0). Export/restore follows the [official Supabase CLI backup guide](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore). Encryption uses [age 1.3.2](https://github.com/FiloSottile/age/releases/tag/v1.3.2). GitHub action major versions are currently pinned as in the repository's existing checks; review and pin their immutable commit IDs before a hardened production rollout.

Default ceilings are 10,000 objects, 50 MiB per object, 250 MiB total unencrypted content, 1,000 buckets and a 60-minute job. Downloads stream through byte counters. Database dumps are size-checked after each CLI export, with a ten-minute timeout per export. Inventory/count changes during the run fail the backup. The final encrypted artifact is capped at 40 MiB; seven daily artifacts use at most 280 MiB, leaving some headroom within shared GitHub storage. Other artifacts and plan changes can still exhaust that quota. A larger backend needs an operator-selected storage destination. These ceilings deliberately fail rather than silently producing a partial backup; review them as usage grows. Only standard object Storage is covered; vector bucket/index data is excluded following Supabase's guide and must have a separate recovery plan if introduced.

The exports use independent logical transactions. Storage inventory is checked before and after, but this is **not** a coordinated point-in-time snapshot across PostgreSQL and object storage. Same-size concurrent file changes or concurrent database updates are not proven absent. Use a controlled maintenance window for the first drill and schema upgrades. Failed runs do not replace a known-good artifact. Seven-day artifact retention is a short recovery window, not archival retention.

## Prepare without exposing secrets

1. On a trusted recovery machine, install `age` and generate a key with `age-keygen -o recovery.agekey`. Keep two private copies outside GitHub, the repository and the app. Save the printed **public recipient** separately. Losing the private identity makes every backup unrecoverable.
2. Create a protected GitHub environment named `backend-backup`. Restrict which branches may use it. Add environment secrets `BACKUP_DATABASE_URL`, `BACKUP_SUPABASE_URL` and `BACKUP_SERVICE_ROLE_KEY`. The URL is the project-specific direct/session-pooler PostgreSQL URL with TLS required; never use the transaction pooler. The service role belongs only to this project and stays in the backup job's environment, never Expo/public variables. The Storage service role has broad authority: use a protected environment and rotate it if exposed. The database login must actually have access to Auth, Storage and application data; do not accept a successful public-only export.
3. Add environment variable `BACKUP_AGE_RECIPIENT` containing the public `age1…` recipient. Do not upload the private identity to Actions. The job only encrypts.
4. Before activation, inspect the workflow, test a disposable project, and obtain approval to store these server credentials. Then set repository variable `BACKUPS_ENABLED=true` and manually run the workflow. Until that flag is set, both manual and scheduled jobs skip. The schedule is 02:23 UTC daily; GitHub may delay or disable inactive scheduled workflows. Monitor failures and verify that successful artifacts remain downloadable.
5. Download the encrypted artifact and verify it on the trusted recovery machine. A GitHub artifact from a public repository must be treated as publicly obtainable even though its contents are encrypted. Keep independent encrypted copies if longer retention is needed. GitHub/Supabase quotas and plan terms can change; this workflow does not guarantee free storage or service forever.

Manual export uses the same script with the five `BACKUP_*` variables (including `BACKUP_OUTPUT_DIR`) supplied by a secure environment. Install Docker, Node 22, `psql`, the pinned CLI and age first. Do not paste credentials into command arguments, commit `.env` files or enable shell tracing. Plaintext is temporarily written to a randomly named private directory with mode 0700 and removed on normal success/failure; use an ephemeral encrypted runner/disk. Unexpected host termination can leave temporary plaintext until that host is destroyed or cleaned.

## Verify the archive

Run `node scripts/verify-backend-backup.mjs /absolute/path/rivl-….tar.age` with `BACKUP_AGE_IDENTITY_FILE` pointing to the private recovery identity. This decrypts into a private temporary directory, rejects unsafe/unexpected archive members, and checks every file, manifest entry and object mapping. It deletes temporary plaintext afterward. It never executes SQL or writes to a database.

Run `node --test scripts/test-backup-manifest.mjs` to check manifest completeness, path handling, checksum rejection and malformed inventories. These tests do not replace the hosted recovery drill.

## Restore only into a disposable project

There is intentionally no unattended destructive restore command. Follow Supabase's linked guide with a new, empty, compatible project and an operator-reviewed copy of the decrypted archive on an encrypted disk. Never point the drill at production.

- Match PostgreSQL/extension and managed Auth/Storage versions. Enable required extensions/webhooks. Restore roles and application schema, then data with triggers disabled using `session_replication_role=replica`, within an error-stopping transaction as prescribed by Supabase. Inspect conflicts rather than ignoring failures.
- `managed-schema.sql` is a reference for custom Auth/Storage policies and triggers. Do **not** blindly overwrite managed schemas. Reapply application customizations from the repository's migrations and compare against that reference. Preserve `supabase_migrations` history separately with the two history files.
- Storage SQL contains metadata, not file bytes. Recreate bucket settings from `inventory.json` and upload each `objects/NNNNNN.bin` to its original bucket/name from `manifest.json`, through the target Storage API. Reconcile metadata with the restored rows; do not assume uploading against existing metadata is automatically compatible across Storage versions. Check MIME/cache settings from the inventory. Never write arbitrary files directly into the provider's internal storage database.
- Vault/column encryption needs special handling. The [official guide's encryption-root-key procedure](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore#restore-backup-using-cli) applies when moving encrypted values. The SQL export alone does not guarantee their decryptability on a different project. Store that recovery material separately or explicitly recreate RIVL worker Vault tokens on the new project after approval. Leave worker cron jobs disabled until secrets and URLs are verified.
- Project settings, SMTP credentials, OAuth-provider configuration, JWT/signing keys, Edge Function environment secrets and deployed function code are not recovered by logical SQL. Restore approved configuration and redeploy functions from the matching repository revision. Reset custom login-role passwords as required by Supabase. Re-enable only the intended publications and scheduled workers.

After manually restoring, rerun the verifier with `BACKUP_VERIFY_TARGET_DATABASE_URL`, `BACKUP_VERIFY_TARGET_SUPABASE_URL` and `BACKUP_VERIFY_TARGET_SERVICE_ROLE_KEY` for the disposable project. The target URL must have a different project reference. The script uses read-only database queries and GET requests: it compares core counts/owner relationships, object metadata inventory and every restored object's bytes/checksum. It does not restore anything.

Finish the drill by signing in as two test users; check owner-private reads, forged-owner denial, community reads, Creator Studio and shared routes, one Storage upload/read/delete, and queue execution after deliberate activation. Verify there are no orphan records and that restored Vault values actually decrypt. Record the source artifact, commit, restore duration, checks and failures in an operations log without credentials or personal data. Only then mark recovery operational. A drill on this repo's tiny temporary PostgreSQL fixture cannot certify hosted Auth, Storage or Vault recovery.
